# Distributed File Sharing System

A Python TCP client/server file-sharing application designed for a cloud VM.
It supports TLS, password authentication, concurrent clients, chunked transfers,
directory operations, and CSV performance logging.

## Features

- Thread-per-client TCP server.
- TLS 1.2+ by default. The client verifies the server certificate.
- Passwords stored as salted PBKDF2-HMAC-SHA256 hashes (300,000 iterations).
- Upload, download, delete, directory listing, create/delete subfolders.
- Upload overwrite confirmation.
- Chunked streaming (1 MiB) suitable for large files; no whole-file buffering.
- Temporary `.part` upload files and atomic replacement after successful upload.
- Server-side transfer metrics in `logs/transfers.csv`.
- Path traversal checks and active-transfer delete protection.

## Requirements

Python 3.10+; OpenSSL for certificate generation. Core application uses only
the Python standard library.

## Local setup

From the repository root:

1. Generate a development certificate:

   ```bash
   bash tools/generate_certificate.sh
   ```

2. Create a user:

   ```bash
   python tools/create_user.py student1 --database server/users.json
   ```

3. Start the server:

   ```bash
   cd server
   python server.py --host 127.0.0.1 --port 5000 \
     --storage storage --users users.json \
     --cert certs/server.crt --key certs/server.key
   ```

4. In another terminal, from the repository root:

   ```bash
   python client/client.py localhost 5000 --ca server/certs/server.crt
   ```

The certificate generated by the helper is valid for `localhost` and `127.0.0.1`.
For remote use, create a certificate whose Subject Alternative Name includes the
server DNS name/IP. Clients should trust the issuing CA/certificate using `--ca`.

### Development-only plaintext mode

You can run the server with `--no-tls` and client with `--insecure` for isolated
local debugging. This sends credentials without transport encryption and must
not be used over public networks or in the cloud.

## Commands

```text
help
dir [REMOTE_DIRECTORY]
upload LOCAL_FILE [REMOTE_PATH]
download REMOTE_PATH [LOCAL_DESTINATION]
delete REMOTE_FILE
subfolder create REMOTE_DIRECTORY
subfolder delete REMOTE_DIRECTORY
exit
```

Remote paths are relative to the server storage root. Example:
`upload lecture.mp4 video/lecture.mp4`.

## File organization and naming

The storage directories are `text`, `audio`, `video`, and `other`. Users may
specify remote paths in these directories. The project brief's TS001/AU001/VD001
naming convention can be added as a metadata/ID layer. This starter preserves
the original filename to make the client interface intuitive; do not silently
rename files without also maintaining a mapping from logical names to stored
paths.

## Protocol outline

Each control message is UTF-8 JSON preceded by a 4-byte unsigned network-order
length. An upload request receives a ready response (or an overwrite/error response) before
the client sends exactly `size` raw bytes; the server sends a completion response
after storing the file. Download responses are followed by exactly the announced
number of raw bytes. This
framing allows control and file data to share one TCP connection without
confusing message boundaries.

## Performance data

The server appends `logs/transfers.csv` with:
- UTC timestamp
- operation (upload/download)
- relative filename
- byte count
- elapsed seconds
- throughput in MiB/s
- username

The client also prints transfer time and throughput. For a fair experiment,
repeat each file-size/concurrency combination several times and report averages.
Test concurrency levels such as 1, 2, 5, and 10 clients. Record VM machine type,
region, network conditions, and file sizes in the report.

## Google Cloud Compute Engine deployment checklist

1. Create a Linux VM and install a supported Python 3 version.
2. Clone the private GitHub repository.
3. Generate/install a certificate with the VM's DNS name or IP in its SAN.
4. Create users on the VM; do not commit `users.json` or private keys.
5. Start the server under a service manager (systemd recommended).
6. Configure the VM firewall to allow the TCP port only from intended client IPs
   where practical. Do not expose SSH or other ports unnecessarily.
7. Test from a remote client using certificate verification.
8. Monitor disk capacity: the required 2 GB video test needs extra room for
   temporary uploads and existing stored files.

Example firewall rule (replace the source range and port appropriately):
allow TCP 5000 only from your campus/home public IP, not `0.0.0.0/0`.

## Known limitations / next improvements

- The current user database provides authentication but not per-user file ACLs.
  Add authorization rules if users should have different permissions.
- `rmdir` only deletes empty directories, intentionally preventing accidental
  recursive deletion.
- For a production system, add upload quotas, disk-space checks, rate limits,
  audit logs for all operations, resumable transfers, checksums (SHA-256), and
  structured protocol versioning.
- This is a teaching project, not a hardened public file-hosting service.
- For production TLS, use a certificate from a trusted CA or your institution.
